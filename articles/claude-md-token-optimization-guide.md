# CLAUDE.md Token Optimization: Why Claude Ignores Your Rules and Where They Should Live
**URL:** https://buildtolaunch.substack.com/p/claude-md-token-optimization-guide
**Track:** AI Builders Playbook
**Published:** 2026-08-29

## Summary

The article starts from a subscriber question about setting up `CLAUDE.md` and `.claudeignore` for token efficiency, which sends Jenny back to check her own earlier advice — and she discovers `.claudeignore` no longer does anything in current Claude Code. She cites a GitHub issue where a user added the file to protect a `.env` file, got no warning or error, and simply had their secrets left exposed, because Claude Code quietly moved this responsibility to `permissions.deny` entries in `.claude/settings.json`. That correction becomes the seed of a broader piece: not just "where do file-exclusion rules live now," but a full model of every place a Claude Code instruction can live and exactly when Claude loads it into context.

She grounds the piece in the published context-window breakdown for a representative 200,000-token session: Claude's own overhead (system prompt, skill descriptions, environment info, deferred MCP tool schemas) totals a little over 5,000 tokens, and the user-controlled layer — project `CLAUDE.md`, auto-generated `MEMORY.md`, and the user-level `~/.claude/CLAUDE.md` — adds about 2,800 more, for roughly 7,850 tokens (about 3.9% of the window) already spent before the first prompt. The project `CLAUDE.md` alone accounts for 1,800 of those tokens, making it the single largest thing a user actually controls. She notes that prompt caching cuts the cost of repeating that middle layer turn to turn to roughly a tenth of standard input pricing, but it does nothing to free up the space those tokens still occupy in the window.

From there she builds a five-layer framework sorted strictly by *when* Claude loads each kind of instruction: plain `CLAUDE.md` content loads at every session start and stays resident for the whole conversation; a rule file under `.claude/rules/` with `paths:` frontmatter loads only when Claude opens a matching file, and without that frontmatter it silently falls back to full always-on loading; skills expose just a short description at startup and pull in their full procedure only when invoked; MCP servers expose tool names at startup and defer full schemas until a tool is actually called; and subagents run in their own separate context window, returning only a summary to the parent — though she flags that most non-fork subagents still reload the entire `CLAUDE.md` hierarchy inside that separate window, so a bloated file gets paid for again on every subagent spawn. Hooks are the one genuinely free layer, since they run outside the model and only cost context if they explicitly return something to it.

The piece then explains why Anthropic's 200-line guidance for `CLAUDE.md` isn't a hard technical ceiling — Claude Code will load a much larger file — but a reliability threshold: longer files give Claude more competing instructions to weigh, and the documentation itself warns that Claude may resolve contradictions arbitrarily. Jenny makes the point that splitting a long file into topic files only helps if those files are pulled in with a plain path reference rather than an `@import`, since imports still get expanded and loaded at session start and therefore save nothing; a bare pointer, by contrast, waits until Claude actually needs it. She applies Anthropic's own line-by-line test — would removing this line cause Claude to make a mistake — as the filter for what's allowed to stay, and for anything that must never be skipped, her answer is to move enforcement into a `PreToolUse` hook rather than trust a sentence buried in a long file to be obeyed every time.

The second half walks through measuring your own setup and rebuilding it: `/context` (and the expanded `/context all`) to see exactly what's loaded and how much space each memory file occupies, `/doctor` to get an automatic proposal for removing repo-derivable content before you approve any change, and an `InstructionsLoaded` hook for a persistent log of what loaded and why, which can only observe, not block. For paid subscribers she includes two companion assets — a downloadable project-setup kit with a filled example repo showing where a `CLAUDE.md`, a path-scoped rule, a skill, a settings file, and a hook script each belong, and a long structured audit prompt that inventories every instruction-bearing file in a project, classifies each line into keep/rule/skill/hook/cut, flags contradictions and unenforceable wording, and only then proposes the rewritten files for approval — but the article stops short of reprinting either as usable text, describing their shape and purpose rather than the exact prompt or scripts sold with the piece. It closes with a three-step maintenance loop: move your most-repeated rule into hook enforcement, relocate one directory-specific rule into a path-scoped file, and re-baseline with `/context` after reloading.
