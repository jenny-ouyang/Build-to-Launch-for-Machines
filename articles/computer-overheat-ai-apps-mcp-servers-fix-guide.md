# If Your Computer Keeps Overheating While Using AI Tools, This Is Why
**URL:** https://buildtolaunch.substack.com/p/computer-overheat-ai-apps-mcp-servers-fix-guide
**Track:** AI Builders Playbook
**Published:** 2026-07-17

## Summary

The article traces an eleven-week Mac overheating problem back to a countable root cause: MCP servers multiplying into hundreds of idle processes. MCP servers are the plug-ins that hand AI apps their tools (email, web search, scraping, payments), and every AI client on the machine (Claude Desktop, Claude Code, Cursor, ChatGPT) starts its own private copy of each configured server, once per session, and most never clean up. Jenny installed 15 servers but her machine was running 797 processes. The symptoms were familiar: free RAM under 200 MB, the compressor holding 6 to 10 GB, and a fan that ran while she did nothing heavier than write markdown. A system-health check came back CRITICAL 29 times out of 37 runs.

Diagnosis starts by getting your own number rather than trusting theory. Two terminal commands do it: `pgrep -f mcp | wc -l` counts every MCP process, and a `ps` plus `grep`/`uniq` pipeline shows which servers they are. Her census read 797, with one Gmail server alone running 123 copies that held roughly 13 GB on a 24 GB machine. Nothing was broken; every process was healthy, idle, and waiting for a session that had already closed. The multiplication had three layers. First, the protocol: MCP's default stdio transport ties each server to one parent process, so it cannot be shared and every session spawns a fresh copy. Second, cleanup: the lifecycle spec says a client SHOULD shut servers down, not MUST, so orphaned copies keep running (a known open issue in Claude Code and Copilot CLI). Third, cross-app import: ChatGPT's Codex engine reads Claude's config and spawns the same fleet from a launch-time snapshot, so one configured server becomes copies across three apps. Five Gmail accounts times sessions times apps is how you reach 123.

Killing the processes never holds. A SIGTERM sweep freed 5.1 GB in seconds, but eighteen hours later the census read 474 because the spawning architecture was untouched. Cleanup scripts also fail because they hunt for orphans and there are none: across the reports the orphan count was often zero while memory ran out, since all 797 processes had a living parent and were legitimate children, invisible to orphan-hunting logic. The rare exception is deletion over architecture: a Cloudflare MCP server with 87 tools pinned a CPU core near 100 percent for hours, so she replaced it with the `wrangler` CLI, which covers the same work with zero idle processes. If a heavy server duplicates a CLI you already have, drop the server.

The real fix is structural: one server, many clients, the same daemon pattern Unix and database connection poolers like PgBouncer have used for decades. MCP's second transport, streamable HTTP, allows one process to handle many client connections. The shared-MCP ecosystem sorts into daemons/brokers, transport bridges, and framework proxies, all of which replace many private copies with one shared instance. Jenny built hers on mcporter (version 0.12.3), from OpenClaw creator Peter Steinberger, because its daemon, HTTP bridge, and stdio shims ship as one tool built together. The setup: install and pin the version, define one server in `~/.mcporter/mcporter.json` with keep-alive lifecycle, `chmod 600` the credential file, start the daemon, and `mcporter serve --http 8848` so each server answers at a local address. Verify every server with a real tool-name call (which caught a search server silently broken for months), add a LaunchAgent so it survives reboots, then wire each client: Claude Code and Cursor take a plain local URL, Claude Desktop and ChatGPT need a thin stdio shim (ChatGPT rejects a URL with "url is not supported for stdio"). The last step that actually ends the sprawl is deleting old stdio entries from every config, since any leftover definition rebuilds itself and ChatGPT copies whatever remains.

Proof comes from a soak test run the next morning, not the same afternoon, since the fleet already regrew from 23 to 474 in eighteen hours once. Three signs confirm it held: a flat count, `mcporter daemon status` showing connected servers with recent activity, and no app spawning its own `npm exec` servers after relaunch (old pre-migration ChatGPT threads respawning their birth config is expected, not a failure). The result: 797 processes down to 15, 13 GB down to under 1, and a health check that had gone CRITICAL 29 times came back clean and stayed clean across a full day of the same work on all four apps, because each server now exists once. The paid MCP Health Kit packages the apparatus as working files: the system-health skill that generated the 37 reports, a migration runbook documenting all five traps, and the working files (mcporter config template, LaunchAgent, and per-client wiring blocks).
