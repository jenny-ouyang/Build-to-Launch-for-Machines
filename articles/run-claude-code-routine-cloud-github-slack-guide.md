# How to Move a Claude Automation From Local to Cloud (Without Breaking the Job)
**URL:** https://buildtolaunch.substack.com/p/run-claude-code-routine-cloud-github-slack-guide
**Track:** AI Agent Systems
**Published:** 2026-09-17

## Summary

This article is Day 3 of a five-day live sprint inside Jenny's Practical AI Builder program, following one recurring Claude Code automation from a bare local proof (Day 1) through connected inputs and outputs (Day 2) to a versioned, cloud-scheduled job. The opening scene is the failure that motivates the whole piece: the first attempt to run the automation as a Claude Remote Routine came back with zero usable results across five source attempts, even though the exact same task had worked perfectly on Jenny's own machine the day before. Rather than treating that as a setback, the article uses it as the teaching hook — a local automation quietly depends on files, credentials, and MCP servers that only exist on the machine running it, and moving to the cloud does not carry any of that context along for free.

The core framework is a five-part model the sprint has been building across all three days: Inputs, Connections, Instructions, Output, and Controls. A remote job needs an approved repository, a working route for every required input, a real output destination, and defined controls — prompt boundary, branch rule, receipt, notification path, schedule, and a pause switch — before it is safe to schedule. Day 3 adds two new action blocks to that model, Synchronize and Maintain, reflecting the fact that a local session, a Slack-invoked session, and a cloud Remote Routine all now need to read the same approved GitHub version, and a person needs a way to inspect, roll back, and pause that version. The article is explicit that a "completed" mark on a cloud run session says nothing about whether the automation actually did useful work, and proposes a six-point proof chain — correct repository, present connections, real output, a separate receipt, a matching Slack notification, and a pause that only lifts after that whole chain passes — as the standard for trusting a scheduled job at all.

The walkthrough itself runs in five graduated steps. First, Jenny creates a private GitHub repository, has Claude propose a minimal safe file boundary (naming what should and should not enter version control, such as tokens and local paths), and reviews and approves the first commit and push. Second, she proves a read-only handoff by installing Claude inside a private Slack channel and issuing a bounded request — read two governing files and reply with status, with edits, branches, and schedule changes explicitly prohibited — to confirm the Slack-to-Claude-to-GitHub path works before any automation is allowed to write anything. Third, she runs the automation as a real Remote Routine for the first time, and it fails exactly as described in the opening: the cloud container starts and reads the repository fine, but the tools tied to Apify and a Gmail newsletter source have no remote route, and public-page fetching is blocked by the remote network policy, producing a zero-source result that she preserves rather than reruns blindly. Fourth, she repairs the job by editing the source configuration to swap in Tavily as a remote-reachable HTTPS input while leaving the rest of the job's logic untouched, and the rerun succeeds, delivering a matching Slack notification partway through the session recording. Fifth, she points the same repository-and-controls pattern at a second, different automation — a topic-research workflow for a separate project — discovers that one runtime lacks access to a required repository, fixes the access, and starts that second job running in the background, stopping the article deliberately short of claiming a finished article or an approved topic, since topic choice and publication are reserved as human decisions for the next day of the sprint.

A secondary thread comes from participant questions during the live session, which the article uses to sharpen a distinction that trips people up: Claude reading from or posting to Slack as part of its own automated session is a different connection than a person invoking Claude from inside a Slack channel and keeping that Code session attached to the thread — the sprint's read-only acceptance test specifically exercises the second direction. The closing section generalizes the pattern into five reusable job shapes — a weekly customer-signal brief, a competitor-change monitor, a content-proposal workflow with a human selection gate, a repository maintenance check, and a scheduled operational report — all organized around the same question: when the computer is closed, what does this job still need to reach, and does that route already exist remotely. The practical takeaway is procedural rather than a tool recommendation: pick one already-working local job, give it a minimal versioned home, prove a read-only path into it, run it once manually before ever turning on a schedule, and treat a remote failure as information about which specific connection needs replacing rather than a reason to abandon the automation.
