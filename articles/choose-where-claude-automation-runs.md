# How to Choose Where Your Claude Automation Should Run
**URL:** https://buildtolaunch.substack.com/p/choose-where-claude-automation-runs
**Track:** AI Agent Systems
**Published:** 2026-09-26

## Summary

The article opens from a live teaching moment: Jenny asked Claude in Chrome to analyze a creator's top Instagram Reels and repeat the analysis weekly, and the request landed as a generic scheduled task rather than a browser shortcut, because naming a cadence is not the same as naming a runner. That gap motivates the whole piece — Claude now offers six different ways to put a job on repeat (`/schedule` and Cowork tasks in the cloud, `/loop` for the active session, local Routines on your own machine, Chrome shortcuts on a signed-in page, and Remote Routines or GitHub Actions inside a repository), and picking the wrong one for a given job's inputs and destinations is what breaks automations that otherwise work. To make the choice legible, Jenny reuses a five-part model that has anchored her whole automation sprint: Inputs (what the job may read), Connections (how it reaches those inputs and delivers a result), Instructions (the procedure and boundaries), Output (the result a person actually uses), and Controls (permissions, proof, duplicate handling, and an off switch). The claim is that this five-part shape stays constant across every runner, so swapping where a job lives should never force you to redesign the job itself — a discipline she names as separation of concerns.

A second thread explains why a second or third automation typically feels harder than the first, even though the underlying skill hasn't dropped. Jenny maps this onto the Dunning-Kruger confidence curve and the Gartner Hype Cycle: an early success inflates both personal confidence and expectations of the tool, and then hidden dependencies — a cloud runner that can't see a local file, a remote repo missing the connections a laptop had, a run that reports success without producing anything useful — surface together and crash both curves at once. Her argument is that the five-part checklist is what turns that crash from a vague "it broke" into a specific diagnosis, by letting you ask separately whether Inputs were reachable, Connections held, Instructions were followed, Output existed, and Controls caught the failure.

The six runner types are then organized around three tests — Access (can it reach every input and deliver through the connections it has), Evidence (does it leave an inspectable receipt separate from the result), and Stop (can it be turned off without a rebuild) — and collapsed into four practical lanes: Claude's own cloud, your computer (loop, local routines, Chrome shortcuts), a repository (Remote Routines, GitHub Actions), and tools beyond Claude entirely (an agent gateway like OpenClaw or Hermes, a workflow tool like n8n or Zapier, or your own hosted code). Each lane is paired with the kind of job that actually fits it and the drawback that rules it out for others — cloud tasks can't see a local folder, local routines need the laptop awake, Chrome shortcuts fail silently if the session signs out, and repository routines don't inherit a laptop's local connections. On top of the routing logic sits a readiness threshold: a job earns a schedule only after one manual run has produced the expected output, the receipt actually points to that output, duplicate behavior is understood, and the pause control has been tested by hand — because a schedule just multiplies whatever behavior you hand it, proof and all.

The most concrete part of the article is a blow-by-blow of that logic failing live, twice, in front of the class. A repository-based routine that should have posted results to Slack passed its repository-access check but stalled because the planned Slack channel wasn't available — a miss the group only found by testing each layer (repository access, command availability, destination access, schedule state) separately and in order. Minutes later, the weekly Instagram Reels request reappeared: Claude first reached for an unrelated research tool before being redirected to just read the page already open, and once the one-off analysis worked, asking to repeat it "weekly" again produced a cloud scheduled task instead of the Chrome shortcut the job actually needed, forcing a manual delete-and-redo. Jenny reads both misses the same way — a failed attempt still tells you which layers are actually available, and similar-sounding requests create different objects depending on which Claude surface hears them, so a scheduling request has to name the surface, not just the interval.

The piece closes by tracing how one recurring job — a research brief that started as a local scheduled task reading Gmail newsletters — grew into a multi-tool pipeline as its inputs widened past what one connector could reach, eventually moving through several research MCPs, then into a version-controlled repository, and finally into a shared operating log once the real gap turned out to be visibility into what had run rather than raw compute. Her point is that most of that evolution was inputs, connections, and controls changing inside the same runner, not the runner itself changing, which is the ordinary and cheaper kind of growth. The actionable takeaway is a short worksheet-style decision sequence — name the next useful result, list the inputs and connections a job actually needs, pick the smallest lane that passes the access/evidence/stop tests, and run one bounded proof before any clock gets attached — packaged for paid members as a fuller set of runtime prompts, decision guides, and blank five-part templates that the free summary intentionally doesn't reproduce.
