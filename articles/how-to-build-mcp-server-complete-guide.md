# Every Way to Build an MCP Server (From the Ones I Actually Shipped)
**URL:** https://buildtolaunch.substack.com/p/how-to-build-mcp-server-complete-guide
**Track:** AI Agent Systems
**Published:** 2026-04-15

## Summary

This is a builder's reference for a question the article argues has no single answer: how do you actually build an MCP (Model Context Protocol) server? Jenny's framing is that every MCP server reduces to one of two transports, stdio (a process that runs on the user's own machine, launched and closed by the AI client) or HTTP (a remote server the client connects to over a URL), and that the five patterns people encounter in the wild — a local script, an npm-published package, a Claude Desktop `.mcpb` installer, an HTTP server with Bearer-token auth, and an HTTP server with OAuth — are just distribution and authentication choices layered on top of those two transports. The article draws that map from six MCPs she has personally shipped, spanning a Substack newsletter MCP, a Substack notes MCP, an article-retrieval MCP, a Gmail MCP, a crossposting MCP, and a paid-member MCP for Build to Launch, and it argues that the real opportunity behind MCP isn't the protocol itself but packaging domain knowledge — the shortcuts and judgment a builder has already refined — into something anyone can plug into their AI client.

The bulk of the piece is a verified, step-by-step build for each pattern, each command marked with a pass/fail status (worked first try, worked after a documented fix, or failed and abandoned) so a reader can tell which steps are trustworthy versus which required a workaround. The stdio build walks from an empty project through a working local MCP server in eight steps, covering the TypeScript and package.json configuration that trips people up (a `module: Node16` setting that's non-negotiable because the MCP SDK imports with `.js` extensions), then shows three ways to ship the same server: pointing Claude directly at the compiled file, publishing it to npm so others install with a single `npx` command, or bundling it as a `.mcpb` file that Claude Desktop installs with a double-click. Each distribution option comes with its own tradeoffs — the `.mcpb` route, for instance, only works with Claude Desktop and ships a static snapshot that requires users to redownload for updates, versus npm which pushes updates automatically on the next install.

The HTTP half of the guide builds the same server twice on different auth models and different hosting platforms, to make the point that the transport is constant while the authentication layer is the variable. The Bearer-token build runs on Next.js and Vercel, with a documented `mcp-handler` security patch and a routing quirk — using a dynamic `[transport]` folder name rather than a fixed `mcp` route — that determines whether older clients connecting over SSE still work. The OAuth build runs on Cloudflare Workers and walks through implementing PKCE (Proof Key for Code Exchange) from scratch: generating and hashing a code verifier, exchanging it for a token, and validating requests, with plain-English framing of what each step in the handshake proves. The article is explicit that OAuth doesn't replace the Bearer token underneath — it replaces the copy-paste, producing the same kind of token but without the user ever seeing it. Three live OAuth MCPs (covering AI builder resources, Substack Notes scheduling, and Substack newsletter search) are cited as running proof that the same PKCE code works unmodified across Cloudflare and Vercel.

Beyond the builds, the article makes an argument about sequencing: don't design for the end state on day one. It traces how her own Substack newsletter MCP moved through all four stages — a fragile hand-rolled Python script, then a `.mcpb` installer, then an npm package, then a fully self-hosted OAuth server — and generalizes that into a decision tree (does the MCP need a backend? if yes, HTTP with Bearer or OAuth depending on whether frictionless sign-in matters; if no, stdio, distributed locally, via npm, or via `.mcpb` depending on the audience's technical comfort). It closes with four spec-level trends to watch in 2026: OAuth becoming a first-class, auto-discoverable part of the protocol, Streamable HTTP replacing the older SSE transport, MCP registries emerging as a distribution layer as important as the build itself, and a breaking v2.0.0 SDK release that wasn't yet production-ready as of publication.

The verdict threaded through the whole piece is pragmatic rather than prescriptive: start with whatever ships fastest, almost always stdio, and graduate to HTTP once a real backend exists, then add OAuth only when the friction of asking users to paste an API key is demonstrably costing adoption. Every MCP she's shipped started simpler than it ended, and the article's structure — templates, gotcha lists, and a comparison table at the end contrasting stdio and HTTP tradeoffs — is built to let a reader skip straight to the one pattern they need rather than read the whole map linearly.
