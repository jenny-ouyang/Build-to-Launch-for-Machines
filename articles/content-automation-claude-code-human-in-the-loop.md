# How to Build a Content Automation System with Human-in-the-Loop
**URL:** https://buildtolaunch.substack.com/p/content-automation-claude-code-human-in-the-loop
**Track:** AI Builders Playbook
**Published:** 2026-09-18

## Summary

This article is Day 4 of a five-day live cohort ("Practical AI Builder") that walks builders through turning one recurring job into a Claude-run automation. Jenny frames the day around a senior content-engineering job description she'd been pitched, one that expected AI to handle daily production while a person kept every consequential call. Days 1 through 3 of the cohort had already built a local routine, wired it to real inputs and outputs, and moved it into a versioned cloud environment; Day 4's addition is the human checkpoint that lets the system change direction without becoming unsupervised.

The piece opens by naming two ways content automation typically fails. Cramming every responsibility, topic choice, research, drafting, voice, fact-checking, and publishing, into one continuous run produces something that looks complete but silently loses track of which stage caused a bad output, and specific failure types (content drift, source drift, voice drift) become indistinguishable from each other. The opposite failure is a minimal pipeline that takes a topic straight to a saved draft, which is easy to build but drops the audience signals, interview material, brand-voice constraints, and sign-off that make the output usable. Jenny's fix is a structure in between the two, splitting a single job into bounded stages with defined inputs, outputs, and handoff points, a practice she ties to published guidance from Anthropic and OpenAI on keeping agent steps small and checkable. Her own diagnostic question for where to cut a boundary is not just how much AI should own, but where the process must stop for a person to decide.

She demonstrates the idea on her own article pipeline for VibeCoding.Builders, which she had already broken from one eleven-phase run into three separate workflows: propose topics, produce the selected article, and record the publication decision, with a person choosing between the first two stages and approving between the second and third. In the live session she kicks off the topic-proposal workflow in front of the class; it returns three candidate topics to Slack, each carrying supporting evidence, an intended reader, and a stated limit, and she replies in-thread to select one. That reply triggers the drafting workflow, which loads the chosen topic and the matching writing skill and is still running when the session ends. The article is candid that the recording only proves the pipeline through that first handoff — it doesn't show the finished article or an approval. What happened afterward is filled in from the repository: the drafting run merged 22 files and about 1,300 lines, produced two draft versions plus a source index and six passing checks, and then stopped itself in a state that waits on a person's publish decision, with no such decision on record inside the window the article covers.

From that worked example, Jenny extracts a repeatable method for readers to apply to their own recurring work: audit a job you've already run and completed, noting every input, decision, output, correction, and point where you waited on someone else; then re-read that audit specifically for where the required information changes, where authority to decide shifts to a different person, or where the next action becomes costly, public, or hard to undo, since those are the true stage boundaries rather than the verbs in a task list. Each resulting stage gets a small contract, naming its trigger, required inputs, allowed work, exact output, and what it must never do before the next human checkpoint. Gates get placed wherever spend, public exposure, or irreversibility appears, and each human decision is written to a durable record, tied to the specific run and to a hash of the exact package being approved, so that any later edit invalidates a stale approval rather than silently carrying it forward. Before scheduling anything, she has readers run the whole path by hand once and specifically try to break it: a normal pass, a missing input, a duplicate run, a requested change, and a reply from the wrong person or the wrong job.

The article's verdict is less about a specific tool and more about discipline: it insists on treating "a workflow is running," "a package is finished," "a package is approved," and "an article is public" as four different, independently provable states, and it uses its own unfinished live demo as proof that those states shouldn't be assumed. It closes by generalizing the same two-gate shape to other recurring jobs, a newsletter issue, a customer story built from an interview, a product changelog, an SEO refresh, and a paid campaign, each needing one point where a person picks the work and one where a person authorizes the result, and it notes from participant questions that the approval gate can be owned by an outside reviewer who never touches the internals, and that a first version of this system should be far smaller than the fully built example. The complete worked example, the automation files, matching skills, decision-record and voice templates, and a recovery guide, sits behind the program's paid membership.
