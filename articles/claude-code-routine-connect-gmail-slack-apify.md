# Supercharge Your Claude Routine With Connectors (and Make It Actually Use Them)
**URL:** https://buildtolaunch.substack.com/p/claude-code-routine-connect-gmail-slack-apify
**Track:** AI Agent Systems
**Published:** 2026-09-16

## Summary

This article is Day 2 of a five-day live "Claude Automation Sprint," picking up a recurring Claude Code routine that Day 1 had already given a local home (a folder with a source list, a procedure file, timestamped output, and a receipt) and asking a harder question: what happens when that routine is handed real, outside data and a real place to report to. The connections in question are a hosted Apify actor for public YouTube data, a Gmail account read in strict read-only mode, and a Slack channel for a completion notification. Jenny frames "connector" more broadly than MCP alone — local files, MCP/API integrations, and stateful services like databases or CRMs are all connections in her map, distinguished mainly by whether the compute runs on your machine or somewhere else, and by whether the routine only reads or also writes. The piece opens by naming the anxiety a lot of readers have around MCP as intimidating infrastructure, and reframes it as the same tool-calling pattern she was already hand-rolling in Cursor with small scripts before MCP existed as a standard.

The article's central argument is that a working connection and a working *routine* are two different claims, and the gap between them is exactly where automations quietly fail. A green "connected" indicator in the UI only proves the first of three needed proofs: access (Claude can reach the source), scope (it reaches the right account, time window, and permitted actions, not a neighboring one), and procedure (the recurring instructions actually say when and how to use the connection). Jenny illustrates the risk asymmetry between the two failure directions — a broken read just produces a thin, disappointing report, while a broken write can put a message somewhere unintended and you find out from another person — which is why the build insists on testing every new connection as an isolated, approved action before it's allowed to run unattended inside the scheduled job.

The live build walks through six steps: inspecting the untouched Day 1 system, connecting and separately testing Apify (retrieving ten videos each from the Anthropic and OpenAI YouTube channels through a capped, priced actor run before anything gets recorded in the source registry), connecting and testing Gmail for a small set of recent newsletter-type emails with private and sensitive categories explicitly excluded, connecting Slack and sending one preview-and-approve test notification, then reconciling the source registry against the procedure file, and finally running the existing scheduled task end to end. Each connector only gets written into the project's `SOURCES.md` registry after its isolated test passes, and the destination (Slack) is treated as supporting evidence for a run rather than the run's real output, which stays a timestamped CSV and Markdown report on disk.

The twist that gives the article its real lesson happens after that reconciliation looks finished: the first full run of the connected routine reported only four consulted sources — the same four from Day 1 — even though Apify and Gmail were both connected and both registered. The cause was a stale line still sitting in the procedure file (`AUTOMATION.md`) explicitly forbidding connectors and third-party research tools, left over from before the sprint, which Claude obeyed exactly as written even though the registry said otherwise. A second, unrelated drift showed up in the same run: the output format had slipped from a clean numbered listicle to a collapsed paragraph, traced to the same root cause of not re-reading the procedure after each change. The fix was a full rewrite of `AUTOMATION.md` into a five-part contract — Inputs, Connections, Instructions, Output, Controls — that reads the current source registry at the start of every run instead of hard-coding what's allowed, removes the obsolete restriction, and pins the report and Slack message formats explicitly.

Notably, the article does not claim a clean win. Jenny reports that the recording ends before a second run could prove all six sources actually get consulted under the corrected procedure, and she deliberately keeps the four-source run as failure evidence rather than overwriting it, framing "prove the fix worked" as the very next step rather than something already demonstrated. The piece closes by generalizing the pattern to other jobs (lead research, cross-channel comparisons, community idea collection, work-signal digests, media intake) and gives a minimal starting checklist — write down the source account and allowed records, the time range and limit, the destination and its approval rule, and the receipt line that proves what a run actually used — before connecting anything at all, arguing that one proven source and one proven destination is the unit that scales, not a big-bang integration of everything at once.
