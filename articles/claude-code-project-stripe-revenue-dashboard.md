# How I Built a Revenue Dashboard From Years of Messy Stripe Payments
**URL:** https://buildtolaunch.substack.com/p/claude-code-project-stripe-revenue-dashboard
**Track:** Products Built and Shipped
**Published:** 2026-08-04

## Summary

Jenny opens by sizing Stripe's reach — hundreds of millions of transactions and tens of billions of dollars processed over a single holiday shopping period, trillions across the year — and notes that it already sits underneath Substack, Circle, Calendly, and Gumroad, meaning most people making money online are touching it indirectly even if they never think about it. What makes it interesting to her as an AI builder specifically is that Stripe exposes a structured REST API, a CLI, and its own MCP server, making it unusually well suited to agent-driven work. Her own account, built up over years across subscriptions, software sales, digital products, memberships, one-on-one payments, and private services, had reached the point where charging worked fine but she could no longer quickly answer which product a given payment belonged to or how any one part of the business was actually trending — so she built a private dashboard to answer that, describing it as the revenue-focused, private-data version of a "data intelligence dashboard" project idea from her earlier list of Claude Code build ideas.

The finished dashboard has four views — revenue by brand, revenue by product stream, monthly gross-versus-net revenue, and a searchable ledger of failed payments kept deliberately separate from settled revenue — with the agent handling code inspection, proposing the classification logic, and running checks, while Jenny personally approves every business label, every grant of live account access, and every financial conclusion drawn from the data. Before touching real money data, she lays out four ways to connect AI to Stripe ranked by how much supervision each needs: a bounded CSV export for answering one fixed question, the official Stripe MCP server for a supervised session inside a client where every write action needs explicit confirmation, the Stripe CLI for local terminal inspection that doesn't help a deployed dashboard stay current once your computer is closed, and the Stripe API for genuinely recurring, scheduled work — which is the route she actually used, since the dashboard needs to refresh on its own. The API key itself never leaves the server side: it's read from a local environment file during development and supplied by the hosting platform's own secrets store after deployment, and neither the browser nor the AI chat session ever sees it. Before any real data flows, she has the agent prove out a restricted, read-only test key against a single bounded check — confirming Stripe accepts the authenticated request without printing back any actual row of data.

Architecturally, she separates three concerns that are easy to blur together: a "source data contract" that defines exactly which Stripe resources and fields the sync is allowed to read (charges, balance transactions, checkout/subscription evidence) and explicitly excludes anything like customer names or addresses; a private database schema that stores normalized money fields alongside business labels, keyed on the Stripe charge ID so a repeated sync updates existing rows instead of duplicating them; and a separate "product map" that turns raw Stripe evidence into the actual brand/stream/product taxonomy she runs her business by. That resolution logic follows a strict, ordered chain of evidence — a payout description rule first, then an approved name pattern, then Checkout product ID, then subscription product ID — and anything that doesn't match any of those falls into an explicit "Other / check" bucket with no confidence assigned, rather than ever being inferred from price or customer identity, which she calls out as specifically unsafe since two different products can share a price.

The build itself runs as a single guided, two-phase process: an initial phase produces a fully clickable, privacy-safe prototype using entirely fabricated placeholder numbers across three structurally different dashboard layouts (an overview-first operator snapshot, a hierarchical product-map view, and an exceptions-first action center), with no Stripe connection, credentials, or real data involved at all — and only after she picks a direction does the second phase wire up the real private product: live restricted keys, the actual sync, the approved product map, and the dashboard views, gated behind explicit approval checkpoints before any live read, database migration, or deployment happens. On top of that one-time build, she documents five recurring, individually bounded and approval-gated workflows that keep the system trustworthy afterward: syncing the private cache (with separate full-import and incremental modes, verified duplicate-free by deliberately re-running an overlapping range); classifying payments against the approved map while keeping unresolved cases visible rather than silently guessed; a weekly revenue review that traces every reported number back to the specific query that produced it; an exceptions review that treats unknown classifications and failed payments as two genuinely different problems, since a failed payment needs follow-up but must never be counted as settled revenue; and a month-end reconciliation that compares Stripe's own totals, the private cache, and the dashboard field-by-field for one fixed period and explicitly refuses to "fix" any mismatch by quietly editing a payment or a mapping rule.

She's candid that a dashboard can render correctly and still be showing stale numbers, which is why she insists the selected reporting period, the last successful sync time, mapping coverage, and reconciliation status stay visibly attached to every figure rather than trusted implicitly — she notes she hadn't personally verified the latest scheduled-sync log at the time of writing and so wasn't willing to call her own dashboard current. The closing sections turn the whole build into a reusable structure: a sixteen-checkpoint build sequence from choosing the right Stripe access route through running all five recurring workflows, each requiring the agent to return proof before moving to the next step; a fill-in checkpoint template for scoping any individual step by its target result, allowed actions, required proof, and stop condition; and three checklists covering mapping integrity, access safety, and dashboard acceptance. She ends by naming the five decisions any reader needs to make to adapt the system to their own business — scope, taxonomy, evidence sources, unknown-handling policy, and the trust threshold a number has to clear before it's used to make a decision — while keeping the underlying one-way data boundary, evidence order, and approval gates unchanged.
